# circuit_mcp — design

*2026-08-24*

## Purpose

An MCP server that checks **my** circuit derivations against a symbolic ground truth,
for a general electronic circuits and systems learning workflow.

Not a solver-for-me. The graded skill is the derivation, so the tool's job is to find
*where* my work diverges — not to hand back an answer.

## Why this shape

An LLM doing small-signal analysis unaided is confidently wrong often enough to be
dangerous in a 4-credit course. A tutor that hands over a wrong transfer function is
worse than no tutor.

So the model never does the math. It sets up the problem and does the parsing;
**lcapy and ngspice are the oracle**. The math is done by something that cannot
hallucinate.

## Design decisions

### 1. Two error classes, two different checks

Setup errors and algebra errors are different failures and need different feedback.
Conflating them produces useless output.

- **Setup error** — the initial equations don't describe the circuit.
  Checked against lcapy's own nodal/MNA system.
- **Algebra error** — step *k* → *k+1* dropped a sign or a term.
  Pure SymPy equivalence. Requires no circuit knowledge at all.
- **Final answer error** — last step ≠ ground-truth `H(s)`.

### 2. Dumb, exact server — the model does the parsing

The MCP server only ever sees clean, unambiguous SymPy expressions. Natural-language
and scribbled math get normalized to SymPy *by the model* before the tool is called.

Translating messy math into SymPy is something a model is reliable at. Deciding
whether two rational functions in `s` are equal is not. Split on that line.
**Do not build a math parser.**

### 3. Two equivalence oracles

`simplify()` is slow and sometimes indecisive on the rational functions that come out
of second-order filters. Pair it with **random numeric substitution** — plug random
values into R, C, s and compare.

- Symbolic (`cancel(together(a - b))`, `ratsimp`) for the proof.
- Random numeric for the safety net, and for a concrete counterexample when they differ.

### 4. Transcribe → confirm → check

When work arrives as an image, **echo the transcription back before running the check.**

Vision reads handwritten math decently, but fails on exactly what circuit derivations
are made of: subscripts, primes, sloppy fraction bars — `v_o`/`v_0`, `R_f`/`R_i`, `ω₀`/`w0`.
A misread yields a confident *"your step 3 is wrong"* when step 3 was fine, which
teaches distrust of correct work. That is the worst failure mode available.

One extra beat turns the weakest link into a visible one.

## Approach: step-chain differ

Paste the derivation as ordered steps. The server checks:

1. Does step 1 match the circuit's actual MNA system?
2. Is each consecutive pair algebraically equivalent?
3. Does the last step match ground-truth `H(s)`?

Output pinpoints the transition: *"step 3 → 4 is where it breaks — you lost the `sRC`
in the numerator."*

Entering with only a final answer and supplying steps on failure is the same tool
surface used at a different entry point, so it comes free.

**Rejected — parallel derivation diff:** independently derive and structurally diff.
There are many valid paths through an op-amp derivation, so it flags
correct-but-different work as wrong. Actively harmful in a tutor.

## Resolved — finite gain-bandwidth (spike, 2026-08-24)

**lcapy will not accept an `s`-dependent component value.** Both the `opamp` variant
and a plain VCVS raise:

```
ValueError: Constant expression A0 / (1 + s/wp) cannot depend on s
```

So it is a general restriction on value fields, not an op-amp quirk.

**The workaround is sound and verified.** Derive with a constant symbol `A`, then
substitute `A -> A(s)` into the resulting expression. Valid because the MNA solve
treats `A` as an opaque symbol either way — there is no differentiation or
integration for the `s`-dependence to interact with.

Verified against a hand-derived ground truth for the inverting amp, agreeing on
*both* oracles (symbolic delta `0`, numeric delta `0`):

```
H(s)  = -A0*Rf*wp / (A0*Ri*wp + Rf*s + Rf*wp + Ri*s + Ri*wp)
DC    = -A0*Rf / (A0*Ri + Rf + Ri)
pole  = -wp*(A0*Ri + Rf + Ri)/(Rf + Ri)   i.e. wp*(1 + A0*Ri/(Ri+Rf))
```

That pole is the gain-bandwidth tradeoff the course actually asks about, so weeks
3-5 are reachable. `srepr` round-trip is exact, so the serialization boundary is
safe if this later goes over HTTP.

Spike: `spikes/lcapy_opamp_spike.py`, `spikes/lcapy_opamp_workaround.py`.

### Two silent-failure traps — both must be guarded

Neither raises. Both return plausible wrong answers, which is the exact failure
mode this tool exists to prevent.

1. **lcapy symbols carry assumptions.** `sympy.Symbol('A')` is not equal to lcapy's
   `A` (which is `positive=True`, etc.), so `expr.subs(Symbol('A'), ...)` silently
   no-ops and returns the expression unchanged. Bind symbols by name out of
   `expr.free_symbols`. **The substitution helper must assert the expression
   actually changed.**

2. **`s` must carry no assumptions.** Declaring `s` as `positive=True` makes
   `solve(denom, s)` return `[]` rather than the pole, because poles are negative
   and SymPy correctly respects the assumed domain. An empty pole list reads as
   "no poles" instead of "wrong domain."

3. **Same name, different assumptions.** SymPy hashes a symbol on its name *and*
   its assumptions, so `Symbol('A')` and `Symbol('A', positive=True)` are
   distinct. Expressions built from each **print identically, character for
   character**, yet never compare equal, and the numeric oracle assigns them
   independent values -- producing a counterexample listing the same name twice
   with different values. The verdict is a confident "your derivation is wrong"
   on correct work.

   This is not hypothetical: it is what happens whenever a freshly parsed
   expression (bare symbols) meets ground truth from lcapy (assumption-carrying
   symbols), which is the normal path once parsing is in play.

   Primary defence is to parse with the reference symbols supplied. As a safety
   net `equivalent()` calls `assert_no_conflicts()` and raises rather than
   returning a verdict; `reconcile(expr, reference)` repairs an expression built
   without them.

   **Refinement:** lcapy's own `s` carries `complex=True, finite=True`. Those do
   not restrict sign and so do not break pole solving (verified: an RC circuit
   still solves to `-1/(C*R)`). A hand-made bare `Symbol('s')` is therefore not
   safer -- it is a *different object* from the `s` inside every lcapy result,
   which made identical expressions raise on any circuit with a capacitor.
   `analysis.S` is now lcapy's own `s`, which satisfies trap 2 and removes trap
   3 at the source rather than patching it downstream.

4. **A DC source with a capacitor silently yields the DC steady state.**
   `Vs 1 0 {V}` on an RC gives a nodal system with no `sC` term at all. An
   s-domain derivation checked against it would be flagged wrong while being
   entirely correct. Write `Vs 1 0 s {V}` for s-domain work.

## Resolved — setup law vs. restated answer (2026-08-25)

`check_setup` passes anything true of the circuit, so writing the final answer
in place of a circuit law passes. The obvious fix is **locality**: a circuit law
involves only one node's neighbourhood, one element, or one loop, whereas the
solved answer reaches across the whole circuit. Netlist topology is available,
so incidence is computable.

It was built and measured, on a corpus of 18 legitimate setups and 6 restated
answers, before being rejected. **No operating point of it is both safe and
useful:**

| scopes allowed | answers flagged | legitimate laws wrongly flagged |
|---|---|---|
| element + node + loop | 0/6 | 0/18 |
| element + node, source-pinned nodes counted as known | 1/6 | 1/18 |
| element + node only | **6/6** | **5/18** |

The last row is the only one that catches anything, and it flags the mesh
formulation the test suite already protects, plus KCL written with the source
voltage substituted — which is how every textbook writes it.

### Why — this is not a weak heuristic, it is the wrong question

For the divider, the law and the answer are *the same equation*:

```
KCL at node 2, source substituted     (V - V2)/R1 - V2/R2      = 0
the solved answer for V2              V2 - R2*V/(R1 + R2)      = 0
ratio                                 -(R1 + R2)/(R1*R2)          <- free of V2
```

A nonzero constant factor apart is not a difference, and *"equations scaled or
reordered or added together"* is listed at the top of `mna.py` as legitimate
variation the tool must never punish. Any rule that flags the second must flag
the first. The same holds for the mesh form (`ratio = -(R1 + R2)`) and for the
RC low-pass (`ratio = -C*s - 1/R`).

Generally: KCL at node *N* is affine in the node voltages. If every node
adjacent to *N* sits at a potential the independent sources fix without solving
the circuit, KCL at *N* is affine in `V_N` alone; it holds at the true solution
and its coefficient is a nonzero sum of admittances; so it *is* `V_N = answer`.
Series circuits with one loop are the same story for the loop current. Those
are most of the circuits the course opens with — so on exactly the examples
where the check would be most used, there is nothing to detect.

### What is shipped instead — report, never reject

`SetupResult.equation_roles` carries one `EquationRole` per equation, and the
`ok` / `underdetermined` message names any that hand over a solved value.
Nothing is rejected on this basis; a restated answer still passes.

The core is provable rather than guessed. The nonlinear refusal already ran, so
the system is affine in the unknowns; a Jacobian row with exactly one nonzero
entry therefore has a unique root, and the satisfaction check has already shown
the equation holds at the true solution. Such an equation *is* `x = answer`,
however it was written. What that means is then decided topologically:

| role | when |
|---|---|
| `law` | couples two or more unknowns, or names nothing outside one element |
| `ambiguous` | fixes one unknown alone, and a circuit law has that same form here |
| `solved` | fixes one node voltage alone, and KCL at that node cannot |
| `trivial` | holds identically |

**Knowns, and their dual.** A quantity is *known* when the independent sources
fix it without solving the circuit. Voltage sources do that for node
potentials, and they chain — two in series pin the far node. Current sources do
it for branch currents, through every element on their series chain. Both must
count: `V1 = Vs` and an op-amp virtual ground `V2 = 0` are one element's own
relation, and `V2 = Iin*R2` is Ohm's law with a known current substituted. Miss
either and a legitimate constitutive relation gets reported as a solved value.

Measured on 24 labelled cases — bridge, supernode, floating source, inverting
and non-inverting op-amp, series RLC, capacitive divider, current-source drive,
stacked sources, cut-set KCL, cleared fractions, alias spellings, reordering —
**24/24**, with zero legitimate laws called `solved`.

### Limits, recorded rather than rediscovered

- **A taught shortcut reads as `solved`.** The voltage-divider rule, the ideal
  op-amp gain formula, and a Thevenin reduction all supply a solved value in one
  line. They are legitimate technique. The wording says only what is true — the
  equation is equivalent to `x = <value>` and no node law at that node has that
  form — and never that the work is wrong.
- **A branch-current unknown is never `solved`.** KVL round a loop carrying it
  can always take that form, so it goes to `ambiguous` unconditionally.
- **The `solved` reason names KCL at that node**, which is what is actually
  checked. It does not claim no law of any kind could have that form.
- **`ambiguous` is a fact about the circuit, not about the student.** It marks
  the case above where the two are one equation.

## Known limits

Recorded so they are expected rather than rediscovered:

- **`Circuit.nodal_analysis()` raises `ValueError: Dependent sources not handled
  yet`** for any E/F/G/H element -- which includes every op-amp, i.e. most of
  this course. `circuit_equations()` returns an empty equation list plus a note
  naming the dependent source instead of pretending. The solved values
  (`c[node].V`) remain available and are the real oracle.
- **`Circuit.symbols` is a shared cache, not per-circuit.** Safe as a name lookup,
  wrong if treated as "the symbols in this circuit".
- **`check_setup` cannot always distinguish derived from merely correct.** A
  student who writes the final answer rather than a circuit law still passes:
  it is true of the circuit and full rank. Each equation is now *classified*
  and the classification reported, but on small circuits the law and the answer
  are provably the same equation -- see "Setup law vs. restated answer" below.
- **Conventions are lcapy's.** Node voltages reference node `0`, and branch
  currents flow into the element's first-named node. A valid setup using a
  different reference node or the opposite current direction reads as an error,
  so the message names the direction assumed.
- **The rank test is a linearisation**, so a system nonlinear in the unknowns is
  refused rather than silently rank-tested.

## Implemented — iPad capture

Work happens on an iPad in GoodNotes. The MCP server now exposes
`workspace_status` and `capture_workspace`: an AirPlay or QuickTime mirror is
captured by macOS `screencapture` and returned as an MCP PNG image. Capture is
request-driven, never a background recording. A SHA-256 hash identifies an
unchanged frame.

The first visual privacy audit proved that full-display capture is too broad: it
included unrelated editor content and the agent conversation. The shipped
default therefore requires an explicit `x`, `y`, `width`, `height` GoodNotes
region. Whole-display capture is refused unless the caller deliberately passes
`allow_full_display=true` for a mirror that occupies that entire display.

The manual path (screenshot → AirDrop or iCloud Drive) remains a fallback.

Findings, so this isn't re-litigated:

- **Controlling the iPad: not possible.** iOS sandboxing exposes no UI automation to
  third parties. Shortcuts is the ceiling. Assume seeing, not touching.
- **Bluetooth: dead end.** No BT profile carries screen content.
- **GoodNotes containers on this Mac are empty** — it syncs via CloudKit's private
  database, not files. Watching that folder does not work.
- **GoodNotes Auto-Backup does not support iCloud Drive** — only Dropbox, Google Drive,
  OneDrive, WebDAV. None currently set up.
- Regular iCloud Drive (`com~apple~CloudDocs`) *is* readable, so *export* to a watched
  folder is viable even though sync-scraping is not.

Capture options considered:

1. **AirPlay mirror + `screencapture`** — implemented; wireless, no install, no
   Developer Mode. A display or privacy-scoped rectangle can be captured.
   Automatic mirror-window discovery remains future work.
2. **QuickTime over USB + `screencapture`** — compatible with the implemented
   capture path. It provides a native-resolution feed
   rather than a scaled mirror. That resolution difference is exactly what decides
   `R_f` vs `R_i`, so wired wins on the one axis that matters.
3. **`go-ios`** (`ios screenshot`) — headless, scriptable, no mirror window. Costs
   Developer Mode plus a `sudo ios tunnel start` daemon on iOS 17+. Not in Homebrew.
4. **`libimobiledevice`** (`idevicescreenshot`) — in Homebrew, but needs a mounted
   Developer Disk Image, which broke on iOS 17+ personalized DDIs. Skip.

`screencapture` requires Screen Recording permission for the host terminal.

### Implemented — local handwriting OCR (2026-08-26)

UniMERNet Small runs in a dedicated `.venv-ocr.nosync` process on native macOS.
It selected PyTorch `mps` on the M4 Max, loaded in 6.9 seconds, reached about
2.47 GB peak resident memory, and transcribed a synthetic inverting-gain formula
correctly. Warm inference measured 0.7–0.8 seconds on that sample.

It must not be imported into the MCP/symbolic process. PyTorch and Metal have a
large, conflicting dependency graph, and initializing a Metal runtime in a
process that later forks is unsafe. Instead the MCP gateway spawns one persistent
OCR interpreter and exchanges framed requests over private pipes. The model is
loaded lazily, survives across requests, is restarted after process death, and
is killed after a 120-second deadline.

UniMERNet 0.2.3 has one Apple-Silicon incompatibility: its `maybe_autocast`
implementation treats every non-CPU device as CUDA and calls
`torch.cuda.amp.autocast`. The worker replaces that helper with a null context on
MPS; tensors and model weights still execute on `mps`.

`transcribe_workspace` composes privacy-scoped capture with OCR and returns both
the exact PNG and generated LaTeX. OCR remains a transcription proposal, never
an oracle. `CLAUDE.md` / `AGENTS.md` require the agent to show the transcription
and wait for student confirmation before calling a mathematical verdict tool.

The empty handwriting benchmark manifest is shipped, but accuracy on the
student's real Goodnotes handwriting still requires labelled samples. Synthetic
typeset success proves the runtime, not handwriting reliability.

## Non-goals

- Schematic image → netlist extraction. Unsupervised structure extraction from
  hand-drawn circuits is unreliable; the netlist gets typed or confirmed.
- Doing homework. If it hands over answers it optimizes for the wrong thing.
- A math parser. See decision 2.

## Environment hazard: iCloud and the venv

`~/Desktop` is iCloud-synced on this machine, and iCloud sets the macOS
`UF_HIDDEN` flag on every dot-prefixed entry, recursively -- `.venv` included.

**Since Python 3.12, `site.addpackage()` stats each `.pth` and silently skips
any with `UF_HIDDEN` set.** So an editable install writes a correct `.pth`
pointing at a directory that exists, and `site` refuses to read it. The import
fails with no diagnostic. `site.addsitedir()` does not help either, because it
delegates to the same `addpackage()` where the check lives.

iCloud also produced nine conflicted-copy artifacts inside site-packages
(`... 2.pth`, `METADATA 2`, `RECORD 2`), most of them cloud-evicted (`dataless`).

Diagnosis: `python -v -c "pass"` prints `Skipping hidden .pth file: ...`.
Immediate fix: `chflags -R nohidden .venv`.
Durable fix: keep the venv out of the synced tree -- move the project off
`~/Desktop`, or name it `.venv.nosync` (iCloud skips `*.nosync`) and symlink.
